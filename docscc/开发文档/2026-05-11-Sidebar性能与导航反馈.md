# Sidebar 性能与导航反馈

> 日期：2026-05-11 · 分类：开发文档 · 状态：已确认

## 背景

用户反馈"菜单点击很卡"。两轮分析 + 修复：第一轮做性能优化，第二轮加导航 loading 反馈。

## 第一轮：性能修复（5 处）

| 问题 | 位置 | 修复 | 影响 |
|---|---|---|---|
| `onToggle={() => toggleGroup(group.group)}` 每次渲染分配新闭包 → `MenuItem` 的 `memo` 永远失效 | `Sidebar.tsx:692` | 改 `onToggle: (groupName) => void`，直接传 `toggleGroup`，让子组件调 `onToggle(group.group)` | 非激活菜单组不再随 Sidebar 重渲 |
| Zustand 全 store 订阅：`const { user } = useAuthStore()` | `Sidebar.tsx:548-549` | 改为 selector：`useAuthStore((s) => s.user)`、`useCrmSidebarStore((s) => s.sidebarCollapsed)`、`...toggleSidebar` 各一行 | Sidebar 只在订阅 slice 变化时重渲 |
| `next/link` 在 30+ 侧栏链接上默认 prefetch → 开发模式触发所有路由并行编译 | `SubMenuItem` + `SubMenuGroup` children | 全部加 `prefetch={false}` | **这是用户感知卡顿的最大单一元凶**：开发服务器编译目标路由时被并行 prefetch 抢占资源 |
| `useReviewQueueCount` 对所有用户都轮询 caseService | hook + Sidebar | hook 加 `enabled` 参数；Sidebar 用 `canSeeComplianceBadge`（按 perms 派生）门控 | 无合规权限的用户不再发起 60s 轮询 |
| `onClick={() => !collapsed ? onToggle() : onToggle()}` 无意义三元 | `MenuItem.tsx:449` | 改为 `onClick={() => onToggle(group.group)}` | 闭包分配消失（语义本来就是一回事） |

## 第二轮：导航 loading 反馈

### 设计目标

**菜单点击不能让用户怀疑"我点了吗"**。两层反馈互补：
- "我的点击有响应吗" → 单项 spinner（瞬时）
- "还要等多久" → 顶部进度条（150ms 后才显示，避免快速导航闪烁）

### Layer 1：顶部全局进度条

新组件：`src/components/crm/layout/NavigationProgress.tsx`
挂载位置：`ClientLayout` 根（覆盖整个 CRM）

**关键设计点**：
- 通过 `mousedown` capture phase 监听 `<a>` 标签 click（捕获时机比 click 早，能感知"按下的瞬间"）
- 同源 / 内部 href 判定后才启动；忽略 modifier-click（Ctrl/Cmd/Shift/Alt → 新标签）、download、`target=_blank`、同 pathname 重复点击
- 150ms 延迟出现，快速导航完全不闪
- 渐进动画：8% 起，每 120ms 朝 80% 滑动，永远到不了 100% —— NProgress 风格的"不会假装完成"
- `usePathname` 变化时 → 填到 100% → fade out → unmount

### Layer 2：单项 spinner

新组件：`src/components/crm/layout/LinkPending.tsx`
调用：`SubMenuItem` 和 `SubMenuGroup` children 的 `<Link>` 内部

实现：`useLinkStatus()`（Next 16 暴露的 hook，必须作为 `<Link>` 后代才能用）。返回 `{ pending: boolean }`，pending 时画一个 `Loader2` 12px。

每个 `<Link>` 有自己的 pending 状态，所以用户点哪个菜单项，spinner 就出现在哪一项 —— 没有"我点了哪个我不知道"的问题。

### 为什么不直接用 router.events

Next 16 App Router 已经移除了 `router.events`。`useLinkStatus` 是官方推荐的替代；全局观察则只能通过 pathname + 自己监听 click。本方案两个都用上了。

## 性能数字（估算）

- 第一轮单点最大改善：开发模式下，单击菜单触发的"路由编译时间窗口"被压缩 → 取决于目标路由大小，大致从"1-2s 卡顿"降到"目标路由首次编译时间"
- prefetch 关闭后，初次加载侧栏不再触发 30 个并行编译，dev server 启动时段的 CPU 占用显著降低
