## 关键设计决策

- **CLM 是合规审核域，不是金融操作域**（来源：产品文档 / CLM 模块定位）
  原因：原模型把 withdrawal_review 塞进 CLMCaseType，导致 Review Queue 混入财务事务；从类型系统拒绝财务 case 进入 CLM 是更稳的边界
- **Configuration 合并到 4 项菜单 + KYCFlow 替代 Policies/Levels/Forms/Templates**（来源：产品文档 / Configuration 简化方案）
  原因：原 7 项过于碎片化，运营反馈"心智门槛高"；Flow 作为唯一的 onboarding 配置单元更直观
- **Re-Verification 规则统一到 Configuration → Routing 第 4 个 tab**（来源：产品文档 / Re-Verification 持续验证）
  原因：四类自动化规则在一处维护，运营看完整个自动化界面只需一次跳转
- **持续验证（continuous）作为 Re-Verification 的新触发类型**（来源：产品文档 / Re-Verification 持续验证）
  原因：证件过期 / 长期不活跃 这类时间维度条件无法靠业务事件触发，需要后台扫描器
- **协议版本号采用 Minor / Major 双 bump 策略**（来源：产品文档 / 协议版本管理策略）
  原因：Minor 是翻译/文案微调，不打扰用户；Major 是实质变更，发布时自动提示开 Force Re-sign 让既存签署者重签
- **Cases 区分自动 / 人工决策（不引入新 storage 字段）**（来源：产品文档 / 审核队列与 Cases 优化）
  原因：现有 `auto_approved` / `auto_rejected` 状态已经表达了语义，衍生函数足够；引入冗余字段反而增加同步负担
- **决策面板风险感知，Reject 在高风险案件升为主按钮**（来源：UI规范 / Case Detail 交互优化）
  原因：默认 CTA 必须匹配低风险路径；高风险案件让 Approve 醒目相当于把审核人推向危险默认
- **同类信息卡用同一种交互范式（hover for popovers）**（来源：UI规范 / Case Detail 交互优化）
  原因：客户元信息卡有多个 popover，原来 IP 是 click / IB 是 hover，不一致让用户摸不清规律
- **侧栏链接关闭 prefetch 是开发模式卡顿的真正解法**（来源：开发文档 / Sidebar 性能与导航反馈）
  原因：next/link 默认对全部 ~30 个侧栏链接 prefetch，开发模式下触发所有路由并行编译，抢占目标页面的资源

### 关键设计决策（下午）

- **所有编辑通过抽屉完成，页面只读摘要**
  原因：文档类型设置和上传设置不应在进入页面时就可直接修改，统一交互范式、降低误操作风险

- **重试次数拆为三字段：单用户总量 + 时间窗口（小时）+ 窗口内次数**
  原因：单一次数无法满足"短时间内刷屏"和"长期累计滥用"两种风控需求，需两套独立阈值

- **活体认证供应商改为枚举（tradepass / onfido / sumsub），外部供应商配置结构化 KEY**
  原因：自由文本无法驱动动态配置 UI；Onfido/Sumsub KEY 字段结构不同，需分别渲染 + 附 SDK 文档链接

- **国家政策 Global 条目置顶 + 缺失时橙色警告**
  原因：未配置 Global 兜底时所有无法精确匹配的用户会被拒绝，属于高危漏配；UI 层必须显式提醒

### 主要变更文件（下午）
