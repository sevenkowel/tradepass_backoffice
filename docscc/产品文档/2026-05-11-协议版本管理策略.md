# 协议版本管理策略

> 日期：2026-05-11 · 分类：产品文档 · 状态：已确认

## 数据模型角色

- `ConfigAgreement` — 协议本体，承载元数据
- `ConfigAgreement.versions[]` — 完整版本历史，每个版本独立带 contents（多语言 body）/ reading（阅读控制）/ signing（签署要求）/ changelog
- `AgreementVersion.status: "draft" | "active" | "retired"` — 三种角色任意时刻同时存在
- `activeVersionId` 是唯一指针；发布会自动把上一个 active 转 retired
- 多个 draft 可以并行存在（v1.0 active + v1.1 draft + v1.2 draft 是合法状态）

## 版本号策略

### Minor / Major 两类 bump

| 类型 | 含义 | 默认 | 发布行为 |
|---|---|---|---|
| **Minor**（默认） | 翻译 / 文案修订 | `v1.0 → v1.1` | 不提示 Force Re-sign |
| **Major** | 实质性变更 | `v1.0 → v2.0` | 发布时自动提示开启 Force Re-sign |

### 自动 bump 规则

- 取所有版本（active/draft/retired 都算）里数字最大的那个为基准
- 不只看数组顺序：用 regex `^v(\d+)\.(\d+)$` 解析，按 (major, minor) 元组排序
- 防御：候选 label 已存在时继续向后递增直到空位（处理"手编未来 label"的极端情况）

### 编辑权限

- 操作员仍可手动改 label —— 自动 bump 只是默认值
- `saveDraft` 校验 label 在协议内唯一；冲突时弹 `alert` 给出冲突版本的 status 信息
- 只有 `status === "draft"` 的版本可编辑；active / retired 是 immutable

## 发布流程（含 Force Re-sign 联动）

```
1. confirm() — 确认发布 + 提示 active 版本会被 retire、signedCount 重置
2. 检测 major bump（targetMajor > activeMajor）
3. 若是 major bump 且 agreement.forceResign 当前为 false：
   confirm() — 询问要不要开启 Force Re-sign 让既存签署者重签
4. 持久化当前 in-flight 编辑（updateVersion）
5. publishVersion（服务端自动 retire 上一个 active、清零 signedCount、更新 currentVersion 指针）
6. 如步骤 3 确认了：update agreement 的 forceResign = true
```

## 列表页支持

### 顶部胶囊筛选

`All (n) · Active (n) · Draft (n) · Retired (n)`，沿用审计中心和 Re-Verification 列表的同款样式。计数永远反映全量，不跟随筛选变化。

### "Draft pending" 提示

active 状态的协议如果同时有 draft 版本（`v1.0 active + v1.1 draft` 这种），卡片头部显示一个 `[GitBranch] 1 draft pending` 蓝色提示芯片。隐藏条件：协议本身已经是 draft 状态（主状态 pill 已经说明了）。

### 操作员行动按钮

- "Open detail" — 进入版本编辑器
- "Edit metadata" — drawer 改元数据
- "Disable / Enable Force Re-sign" — 全局开关

## 版本编辑器（详情页 Versions tab）

- 左侧 timeline 列出全部版本，每条带 status 芯片和签署计数
- 顶部"新建草稿"按钮拆成两个：**Minor**（slate）和 **Major**（amber）
  - 鼠标悬停 tooltip 预览将创建的 label
- 右侧编辑区：版本 label（draft 可改）/ 多语言 body / changelog
- 多语言 tab：当前 draft 时可加 / 删除语言；retired / active 只读
